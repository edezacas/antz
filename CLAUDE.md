# antz

## Overview
`antz` defines a spec-driven development (SPDD) workflow with three role agents — **specifier** writes behavior specs, **coder** implements one sub-spec at a time, **verifier** validates and merges — plus a fourth, **orchestrator**, that sequences the other three for one change and is the recommended entry point (via `/antz`). No application code lives here yet — this repo *is* the agent definitions, kept client-agnostic so they can be installed into Claude Code, OpenCode, or other agent runners.

## Stack
- Plain text/YAML, split by concern: prompt body (client-agnostic) vs. metadata (name/description/access), rendered by `install.sh` into each client's native frontmatter.
- No build system, package manager, or runtime — nothing to compile. `install.sh` is a POSIX `sh` script (works via `curl | sh`, no bash-only syntax).

## Structure
- `agents/prompts/{specifier,coder,verifier,orchestrator}.prompt` — the role instructions verbatim (no frontmatter, no client-specific syntax). This is the single source of truth for behavior.
- `agents/meta/{specifier,coder,verifier,orchestrator}.yaml` — `name`, `description`, `access` (`readonly`, `readwrite`, or `orchestrateonly`) per role. `access` is the abstract capability a generator maps to each client's tool/permission model (e.g. Claude Code `tools:` list, OpenCode `permission:` block + `mode`).
- `spdd/{changes,specs,archive}/` — not present yet; created on first run of the workflow (specifier creates `spdd/changes/<slug>/`; verifier creates/updates `spdd/specs/` and `spdd/archive/`).

## Gotchas
- Strict directory ownership: coder only reads `spdd/changes/` and must never touch `spdd/specs/` or `spdd/archive/`; verifier merges into specs and archives changes, but never overwrites a domain spec file wholesale (merge scenario-by-scenario, ADD/MODIFY/REMOVE).
- Open questions from the specifier live at the fixed path `spdd/changes/<change-slug>/OPEN_QUESTIONS.md`. Its mere presence — not its contents — is a hard stop: the coder must not implement anything in that change while the file exists. The specifier only creates it when something is genuinely blocked, and must delete it once every question is resolved; a stale file blocks work that's no longer actually blocked.
- coder handles exactly one sub-spec per session — if handed a full multi-layer plan, it's supposed to refuse and ask for a single sub-spec.
- `access` is `readonly | readwrite | orchestrateonly`. The specifier, coder, and verifier roles are all `readwrite` — edit capability, each for its own prompt-owned artifact surfaces: the specifier authors `spdd/changes/<slug>/`, the coder implements sub-specs, the verifier merges into `spdd/specs/` and owns `spdd/archive/` moves and `REJECTED.md` appends; the orchestrator role remains `orchestrateonly` — readonly-equivalent tools plus a delegation capability, used only by it. The safety boundary is prompt-level path ownership per role plus the never-commits law, not tool absence — framework permissions cannot scope edits to paths, and granting Edit/Write grants artifact authorship, never commit authority. Keep this mapping in mind when generating framework-specific frontmatter — it's the capability model the whole workflow depends on.
- Skills activation (coder and verifier): both roles discover the available skills before planning/verifying and activate any skill whose description matches the code or files about to be written, modified, or judged — matched by description, never by a hardcoded skill name. The enablement is mechanical: the rendered `readwrite` Claude grant includes the `Skill` tool (a subagent `tools:` list is an enforced allowlist on Claude Code), while OpenCode agents get the client's native skill tool by default; on a client without a skill tool, the fallback is a directory listing — the roles enumerate the working root's and the user's skills directories (`.agents/skills/`, `~/.agents/skills/`, `.claude/skills/`, `~/.claude/skills/`, `.opencode/skills/`, `~/.config/opencode/skills/`) and read the matched `SKILL.md` in full (paths, not summaries). Orchestrated (via `/antz`) delegations carry a pre-resolved `## Skills to load before work` block with absolute `SKILL.md` paths, derived mechanically from those standard skills directories at delegation time (paths, not summaries), with an explicit `Skills: none matched` line when no skill matches; no persistent registry file is kept and no refresh hook, plugin, or CLI is introduced — freshness comes from per-delegation derivation, and `install.sh` never mutates user configuration (`settings.json`, permission blocks) for this. Each role's own report states which skills were activated (by name) or that none matched — a transparency line only, never a routing input.
- OpenCode structurally diverges for the orchestrator: it's `mode: primary` (the other three are `mode: subagent`), because OpenCode's stable, documented path for an agent to invoke subagents is a `mode: primary` agent using `permission.task` — subagent-to-subagent delegation is a newer, version-dependent feature not safe to rely on. `permission.task` scopes *which* agents it may delegate to via a glob-pattern-keyed object, deny-by-default, allowing only `antz-specifier`/`antz-coder`/`antz-verifier` by exact name (evaluated last-match-wins) — this is genuinely enforced at runtime on OpenCode.
- **Claude Code asymmetry (known, accepted platform limitation, not a bug to fix later)**: the orchestrator's `tools:` grants plain, unrestricted `Agent` — the `Agent(name, ...)` allowlist syntax only scopes spawning for an agent running as the main thread via `claude --agent`, and is silently ignored for a subagent, which `antz-orchestrator` always is (invoked via `/antz` or auto-delegation from the main session). So on Claude Code, staying within the three role agents is a prompt-level instruction only (`orchestrator.prompt`'s "What you don't do"), not a tool-enforced boundary.
- `spdd/changes/<change-slug>/REJECTED.md` — like `OPEN_QUESTIONS.md`, written by a role rather than the orchestrator, but unlike it, not presence-only: `verifier` *appends* one entry per rejection (never overwrites), each headed by its own line reading exactly `## Rejection <n>` (a literal, machine-countable heading, not just "numbered" in spirit) with the reported blockers on the lines that follow. The entry count is the orchestrator's bounded-retry counter, read fresh from disk on every invocation via `orchestrator.prompt`'s probe script (source of truth: `scripts/orchestration/antz-probe.sh`; see below): 1 entry → relay the attributable blockers to `coder` and retry `verifier` once; 2 entries → stop for good, never invoke `coder` or `verifier` again for that change. Within an entry, a blocker that doesn't trace to a single sub-spec (cross-feature coherence, an e2e QA step) is marked as such — an entry holding one makes the one retry a manual, user-invoked `verifier` pass instead of an orchestrated one (the orchestrator stops and reports that resume action rather than delegating); a rejection of that manual pass still appends the second entry, so the count reaches 2 and stops for good either way.
- `orchestrator.prompt` runs a small POSIX `sh` probe script (source of truth: `scripts/orchestration/antz-probe.sh`, whose content `install.sh` injects into the rendered `antz-orchestrator` body for both clients; same runtime convention as `/antz-set-model`'s embedded script: saved to a temp file and run via `sh`, rather than installed anywhere) that computes the disk-derivable facts mechanically instead of describing the procedure in prose: `OPEN_QUESTIONS.md` presence, `REJECTED.md`'s entry count, and each sub-spec's declared scenario ids plus its receipt classification fields (ids read from the first line of the comment tag immediately above each `Scenario:`/`Scenario Outline:` — tag continuation lines are description, not ids; the receipt fields `receipt=`/`covered=`/`complete=`/`class=` read from the coder's `NN-<feature>.result` receipts). It deliberately stops short of running the unit suite itself — the receipts are read as files, like everything else it reports, and classification is mechanical from their fields; discovering a project's own test command is `coder`'s job, recorded in each receipt's `test_command=`, since antz is language/framework-agnostic and a script can't know that convention up front.
- The `BLOCKED: <why>` skip-reason convention: no new file — just a distinguishable reason (plain colon, not an em dash) on the `skip`/`pending` stub `coder` already writes when it refuses or escalates instead of finishing a scenario, or when it refuses a whole sub-spec at the planning stage before any test exists yet. It marks a status distinct from an ordinary skip: the orchestrator must not re-delegate that sub-spec to a fresh `coder` session.
- Two more disk-only conventions the orchestrator's state machine depends on: `specifier` numbers sub-spec filenames by dependency order (`01-api.feature`, `02-client.feature`, ...), and `coder` tags every test name with its scenario's `<feature>-<index>` id (never only in a comment, which doesn't surface in test-runner output). Classifying a sub-spec in-progress vs. done reads the receipt the coder wrote for it (`spdd/changes/<slug>/NN-<feature>.result`, see the Receipts bullet below) — grounded in the unit-level suite the coder actually ran, and only that suite, never the specifier's end-to-end QA suite, which `coder` is explicitly excluded from (that's `verifier`'s job during Integration Verification).
- Receipts (`spdd/changes/<slug>/NN-<feature>.result`) — written by the coder role at the end of each session that finishes or advances a sub-spec (named after the sub-spec file, `01-api.feature` → `01-api.result`; a later session on the same sub-spec rewrites it in place): one `test_command=<discovered unit-suite run command>` line plus one `id=<feature>-<index> result=green|skip|blocked reason=<text>` line per declared scenario id (exact declared id set, non-empty reason on every line; blocked reasons carry the existing `BLOCKED:` convention). The disk receipt is the classification authority: the probe reads the receipts and emits `receipt=/covered=/complete=/class=` per sub-spec, and the orchestrator classifies by reading them — running the unit suite only for a doubtful receipt (missing/incomplete/mismatched), never for classification of a well-formed receipt and never as a pre-verifier gate.
- Closing block: every role's conversational report ends with a grep-able block of exactly three consecutive lines — `status=<value>`, `ids=<id,id,...>`, `results=<value>` — with per-role value vocabularies pinned in the role prompts (specifier: `spec_complete` / the declared ids of the sub-specs it wrote / `none`; coder: `done|blocked` / its sub-spec's declared ids / `id=<id> result=<green|skip|blocked>` tokens mirroring its receipt, in receipt order; verifier: `approved|rejected` with approved-with-warnings folding to `approved` while the prose verdict stays authoritative / the change's declared ids / tokens from the receipts as found on disk at verification end; orchestrator: `delegated-specifier|delegated-coder|delegated-verifier|stopped|released|waiting-user` / the ids from the probe / `<subspec-file>=<done|blocked|in_progress>` from the probe's class fields). The closing block is a transparency mirror only, never an input to any routing state or count: no routing, count, or decision ever derives from it, and wherever a disk receipt exists, the receipt is the authority over the block's mirrored values — the governing rule extends to the block.
- **Branch-marked flow, never committed (`4.0` behavior)**: each change gets its own marker branch `antz/<slug>` at the commit the flow started from, created **and checked out** by the orchestrator's `antz-flow.sh` (`ensure`; source of truth: `scripts/orchestration/antz-flow.sh`, whose content `install.sh` injects into the rendered `antz-orchestrator` body for both clients — runtime unchanged: saved to a temp file and run via `sh <tempfile> ...`, nothing installed as a standalone CLI/hook/plugin) — the flow's session sits on `antz/<slug>` with all the work uncommitted in the working tree; on resume, `ensure` re-positions the session onto the existing branch (whose ref is never rewritten). A refused positioning — switching would overwrite uncommitted changes — stops the flow with a machine-readable state (`state=checkout_refused`) and never forces anything. Under stable law: no `-B`, no `--force`, no merges, no resets, no branch deletes, and never a forced or overwriting checkout — and above all **no role ever commits anything**: the work stays uncommitted in the working tree, and committing it is the human's follow-up. The slug is imposed on the specifier per-invocation (suffix automatically only to avoid a blanket collision, never as a git-branch alias without human sign-off). The flow has no unbranched fallback: `antz-flow.sh`'s preflight fail-closes every subcommand with `state=no_git` (git not on PATH) or `state=no_repo` (not inside a git repository) — the orchestrator stops and hands `git init`/initial commit back to the human. Resume state is the working tree's `spdd/changes/<slug>` (branch trees are always identical to the flow's base commit, so `discover` lists both `candidate=branch` markers and `candidate=on-disk` change dirs). antz has a sibling variant in the `worktree` branch — worktree isolation with gated per-role commits — maintained in parallel; docs `docs/worktree-isolation-plan*.md` describe it historically.
- **No commits, any phase (`3.0` behavior)**: no role carries a commit fence anymore — `antz-commit.sh` and the `## Committing` sections are gone from all three role prompts, so manual/direct invocations and orchestrated flows alike never commit anything (committing is always the human's follow-up). This is the deliberate contract split from the `worktree` sibling variant, which keeps gated per-role commits.
- Release gating, never speculative: after an approved Merge & Archive, the orchestrator runs `release`, and the shim reads `spdd/archive/<slug>` (must exist) and `spdd/changes/<slug>` (must not) from the working tree, refusing unless the marker branch exists — any check failure is stop-and-report. Nothing is ever removed: the branch marker survives for the human's bookkeeping. The follow-ups are all the user's own, run in their own session: the user is already on `antz/<slug>` (ensure positioned the session there), reviews the pending files in `git status`, commits whenever and how they prefer, then themselves decide whether and where to merge (e.g. `git switch <integration> && git merge antz/<slug>` — `<integration>` is a placeholder, never a hardcoded branch name) and may delete the branch. The orchestrator never merges and never resets a branch, and never runs those follow-ups itself.
- **Governing rule**: no role, including the orchestrator, may depend on another role's conversational output — every invocation starts with empty context, so all cross-role state lives on disk (filenames, test names/results, `OPEN_QUESTIONS.md`, `REJECTED.md`, directory location).

## Client Integration
- Neither `agents/prompts/` nor `agents/meta/` is itself a Claude Code or OpenCode subagent file — `install.sh` renders each `<name>.prompt` + `<name>.yaml` pair into the frontmatter each client needs (Claude Code: `name`/`description`/`tools:`; OpenCode: `description`/`mode`/`permission:`) and installs to that client's global agents directory. `access: readonly` maps to no edit/write capability; `access: readwrite` maps to full edit access plus, on Claude Code, the `Skill` tool grant (on OpenCode, agents inherit the client's native skill tool by default); `access: orchestrateonly` maps to readonly plus a delegation capability — see `install.sh` for the exact mapping, and the Gotchas above for the Claude Code/OpenCode asymmetry in how that delegation is scoped. After this change no role declares `readonly` (the four meta files declare only `readwrite` and `orchestrateonly`), but `install.sh` keeps the mapping: it remains a defined level.
- Files `install.sh` writes carry an `antz:generated` marker comment inside the frontmatter; re-running it overwrites those in place but backs up (`.bak.<timestamp>`) any pre-existing file with the same name that lacks the marker, rather than clobbering it.
- `install.sh` works both from a local checkout (reads `agents/` directly) and via `curl | sh` (fetches from `RAW_BASE` in the script, currently GitHub `master`). `VERSION`/`CHANGELOG.md`/tagging are tracked per branch: `master` is the branch-marked, no-commit variant; the `worktree` branch is the worktree-isolated variant with gated per-role commits, and binds its remote install to its own ref via its own `REPO_BRANCH`. Keep both refs in sync if the repo location changes.
- Installed agent names carry an `antz-` prefix (`antz-specifier`, `antz-coder`, `antz-verifier`, `antz-orchestrator`, set via `name:` in `agents/meta/*.yaml`) — deliberately, so they don't collide with a user's own or another package's generically-named `specifier`/`coder`/`verifier`/`orchestrator` agents. Source files under `agents/prompts/` and `agents/meta/` keep the unprefixed role names; only the rendered/installed name is prefixed.
- `/antz` is the recommended entry point in both clients, installed to `~/.claude/commands/antz.md` and `~/.config/opencode/commands/antz.md` via the same `install_file`/marker/backup mechanism as agent files. The mechanism differs per client: on Claude Code the command body runs in the main session (which already has the `Agent` tool) and explicitly delegates the request to the `antz-orchestrator` subagent; on OpenCode the command's `agent: antz-orchestrator` frontmatter (with no `subtask`) switches the session to that `mode: primary` agent natively instead of spawning it as a nested subagent.

## Versioning
- `VERSION` (semver) and `CHANGELOG.md` (Keep a Changelog format) track changes to `agents/prompts/`, `agents/meta/`, and `install.sh`. Any commit that changes any of those three must bump `VERSION` and add a matching `CHANGELOG.md` entry in the same commit, regardless of what else that commit contains (a commit touching `agents/` and/or `install.sh` together with docs or tests is still a bump commit). The patch/minor/major gradation is one scale for `agents/` and `install.sh` changes alike: patch for non-behavioral wording tweaks, including `install.sh` comment/string-only tweaks and internal refactors with no change to rendered output or reported behavior; minor for behavior changes, to the roles or to `install.sh`'s install mechanics and rendered commands/agents (rendered bodies, flags, install paths, detection logic, the `--check` report); major for breaking changes to the workflow contract or the rendered command contract (directory layout, access model, the `antz:generated` marker format, the access-to-frontmatter mapping, install locations, etc). A commit touching several tracked paths grades by its most severe component. Changes to docs (`AGENTS.md`, `CLAUDE.md`, `docs/`, `spdd/`) and to `tests/` don't require a bump. Why `install.sh` is tracked: it renders the installed agent and command files directly and embeds the source `VERSION` in each installed file's `antz:generated` marker comment, so an unbumped `install.sh`-only change leaves installed copies silently stale — `./install.sh --check`'s version comparison reports no drift, and the documented bump rule is the only defense against that.
- `install.sh` embeds the source `VERSION` in each installed file's marker comment. Every run compares that to the installed copy's embedded version and, if newer, prints the intervening `CHANGELOG.md` entries before overwriting. `./install.sh --check` only prints that report — no files are written.
- Every `VERSION` bump gets a matching git tag (`vX.Y.Z`) created locally against the commit that makes the bump, in the same change — tags aren't pushed automatically, only on explicit request. `VERSION`/`CHANGELOG.md`/tags diverge per branch: `master` (the branch-marked, no-commit variant) counts forward from 3.0.0, the `worktree` branch (the worktree-isolated variant) continues its own line from 2.5.0.
