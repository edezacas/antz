# antz

## Overview
`antz` defines a spec-driven development (SPDD) workflow with three role agents — **specifier** writes behavior specs, **coder** implements one sub-spec at a time, **verifier** validates and merges — plus a fourth, **orchestrator**, that sequences the other three for one change and is the recommended entry point (via `/antz`). No application code lives here yet — this repo *is* the agent definitions, kept client-agnostic so they can be installed into Claude Code, OpenCode, or other agent runners.

## Stack
- Plain text/YAML, split by concern: prompt body (client-agnostic) vs. metadata (name/description/access), rendered by `install.sh` into each client's native frontmatter.
- No build system, package manager, or runtime — nothing to compile. `install.sh` is a POSIX `sh` script (works via `curl | sh`, no bash-only syntax).

## Structure
- `agents/prompts/{specifier,coder,verifier,orchestrator}.prompt` — the role instructions verbatim (no frontmatter, no client-specific syntax). This is the single source of truth for behavior.
- `agents/meta/{specifier,coder,verifier,orchestrator}.yaml` — `name`, `description`, `access` (`readonly`, `readwrite`, or `orchestrateonly`) per role. `access` is the abstract capability a generator maps to each client's tool/permission model (e.g. Claude Code `tools:` list, OpenCode `permission:` block + `mode`).
- `spdd/{changes,specs,archive}/` — not present yet; created on first run of the workflow (specifier creates `spdd/changes/<slug>/`; verifier creates/updates `spdd/specs/` and `spdd/archive/`).

## Gotchas
- Strict directory ownership: coder only reads `spdd/changes/` and must never touch `spdd/specs/` or `spdd/archive/`; verifier merges into specs and archives changes, but never overwrites a domain spec file wholesale (merge scenario-by-scenario, ADD/MODIFY/REMOVE).
- Open questions from the specifier live at the fixed path `spdd/changes/<change-slug>/OPEN_QUESTIONS.md`. Its mere presence — not its contents — is a hard stop: the coder must not implement anything in that change while the file exists. The specifier only creates it when something is genuinely blocked, and must delete it once every question is resolved; a stale file blocks work that's no longer actually blocked.
- coder handles exactly one sub-spec per session — if handed a full multi-layer plan, it's supposed to refuse and ask for a single sub-spec.
- `access` is `readonly | readwrite | orchestrateonly`. `specifier`/`verifier` are `readonly` (no edit/write capability); `coder` is `readwrite` (the only role that modifies files); `orchestrator` is `orchestrateonly` — readonly plus a delegation capability, used only by it. Keep this mapping in mind when generating client-specific frontmatter — it's the safety boundary the whole workflow depends on.
- OpenCode structurally diverges for the orchestrator: it's `mode: primary` (the other three are `mode: subagent`), because OpenCode's stable, documented path for an agent to invoke subagents is a `mode: primary` agent using `permission.task` — subagent-to-subagent delegation is a newer, version-dependent feature not safe to rely on. `permission.task` scopes *which* agents it may delegate to via a glob-pattern-keyed object, deny-by-default, allowing only `antz-specifier`/`antz-coder`/`antz-verifier` by exact name (evaluated last-match-wins) — this is genuinely enforced at runtime on OpenCode.
- **Claude Code asymmetry (known, accepted platform limitation, not a bug to fix later)**: the orchestrator's `tools:` grants plain, unrestricted `Agent` — the `Agent(name, ...)` allowlist syntax only scopes spawning for an agent running as the main thread via `claude --agent`, and is silently ignored for a subagent, which `antz-orchestrator` always is (invoked via `/antz` or auto-delegation from the main session). So on Claude Code, staying within the three role agents is a prompt-level instruction only (`orchestrator.prompt`'s "What you don't do"), not a tool-enforced boundary.
- `spdd/changes/<change-slug>/REJECTED.md` — like `OPEN_QUESTIONS.md`, written by a role rather than the orchestrator, but unlike it, not presence-only: `verifier` *appends* one entry per rejection (never overwrites), each headed by its own line reading exactly `## Rejection <n>` (a literal, machine-countable heading, not just "numbered" in spirit) with the reported blockers on the lines that follow. The entry count is the orchestrator's bounded-retry counter, read fresh from disk on every invocation via `orchestrator.prompt`'s embedded probe script (see below): 1 entry → relay the attributable blockers to `coder` and retry `verifier` once; 2 entries → stop for good, never invoke `coder` or `verifier` again for that change. Within an entry, a blocker that doesn't trace to a single sub-spec (cross-feature coherence, an e2e QA step) is marked as such — an entry holding one makes the one retry a manual, user-invoked `verifier` pass instead of an orchestrated one (the orchestrator stops and reports that resume action rather than delegating); a rejection of that manual pass still appends the second entry, so the count reaches 2 and stops for good either way.
- `orchestrator.prompt` embeds a small POSIX `sh` probe script (same embedded-script convention as `/antz-set-model`'s: saved to a temp file and run via `sh`, rather than installed anywhere) that computes the disk-derivable facts mechanically instead of describing the procedure in prose: `OPEN_QUESTIONS.md` presence, `REJECTED.md`'s entry count, and each sub-spec's declared scenario ids (read from the first line of the comment tag immediately above each `Scenario:`/`Scenario Outline:` — tag continuation lines are description, not ids). It deliberately stops short of running the unit suite or classifying pass/fail/`BLOCKED` itself — discovering and interpreting a project's own test command stays a judgment call the orchestrator makes per project, since antz is language/framework-agnostic and a script can't know that convention up front.
- The `BLOCKED: <why>` skip-reason convention: no new file — just a distinguishable reason (plain colon, not an em dash) on the `skip`/`pending` stub `coder` already writes when it refuses or escalates instead of finishing a scenario, or when it refuses a whole sub-spec at the planning stage before any test exists yet. It marks a status distinct from an ordinary skip: the orchestrator must not re-delegate that sub-spec to a fresh `coder` session.
- Two more disk-only conventions the orchestrator's state machine depends on: `specifier` numbers sub-spec filenames by dependency order (`01-api.feature`, `02-client.feature`, ...), and `coder` tags every test name with its scenario's `<feature>-<index>` id (never only in a comment, which doesn't surface in test-runner output). Classifying a sub-spec in-progress vs. done requires actually running `coder`'s unit-level test suite, not just grepping for the id — and only that suite, never the specifier's end-to-end QA suite, which `coder` is explicitly excluded from (that's `verifier`'s job during Integration Verification).
- **Worktree isolation (2.0 behavior)**: each change runs in its own worktree `.worktrees/<slug>` on branch `antz/<slug>`, both created by the orchestrator's embedded `antz-flow.sh` (`ensure`) — no `-B`, no `--force`, no prune, no merges from the orchestrator; the slug is imposed on `specifier` per-invocation (auto-suffix only to avoid a collision, never as a git-branch rename without human sign-off). No non-isolated fallback: the flow script's preflight fail-closes every subcommand with `state=no_git` (git not on PATH) or `state=no_repo` (not inside a git repository) — stop and hand `git init`/initial commit to the human.
- **Per-role commits (gated on the working root)**: the three roles commit via a shared `antz-commit.sh` fence in their own prompts — without a working root (WORKING_ROOT unset) the gate stays closed (exit 1, nothing committed), so manual/direct invocations never auto-commit. No staging sweeps are possible: the script takes only exact-path args and refuses empty staged trees.
- Worktree removal is a single disk-checked gate: after an approved Merge & Archive, the orchestrator's `release` reads `<worktree>/spdd/archive/<slug>` (must exist) and `spdd/changes/<slug>` (must not) — any mismatch (archive missing, change still present, path mismatch) is stop-and-report, never `--force`.
- The branch survives what the worktree doesn't: merging (to the human-chosen integration branch, name never hardcoded) and `git branch -d antz/<slug>` are the human's follow-up. The orchestrator never merges, never deletes a branch, never resets one.
- **Governing rule**: no role, including the orchestrator, may depend on another role's conversational output — every invocation starts with empty context, so all cross-role state lives on disk (filenames, test names/results, `OPEN_QUESTIONS.md`, `REJECTED.md`, directory location).

## Client Integration
- Neither `agents/prompts/` nor `agents/meta/` is itself a Claude Code or OpenCode subagent file — `install.sh` renders each `<name>.prompt` + `<name>.yaml` pair into the frontmatter each client needs (Claude Code: `name`/`description`/`tools:`; OpenCode: `description`/`mode`/`permission:`) and installs to that client's global agents directory. `access: readonly` maps to no edit/write capability; `access: readwrite` maps to full edit access; `access: orchestrateonly` maps to readonly plus a delegation capability — see `install.sh` for the exact mapping, and the Gotchas above for the Claude Code/OpenCode asymmetry in how that delegation is scoped.
- Files `install.sh` writes carry an `antz:generated` marker comment inside the frontmatter; re-running it overwrites those in place but backs up (`.bak.<timestamp>`) any pre-existing file with the same name that lacks the marker, rather than clobbering it.
- `install.sh` works both from a local checkout (reads `agents/` directly) and via `curl | sh` (fetches from `RAW_BASE` in the script, currently GitHub `master`) — keep that URL in sync if the default branch or repo location changes.
- Installed agent names carry an `antz-` prefix (`antz-specifier`, `antz-coder`, `antz-verifier`, `antz-orchestrator`, set via `name:` in `agents/meta/*.yaml`) — deliberately, so they don't collide with a user's own or another package's generically-named `specifier`/`coder`/`verifier`/`orchestrator` agents. Source files under `agents/prompts/` and `agents/meta/` keep the unprefixed role names; only the rendered/installed name is prefixed.
- `/antz` is the recommended entry point in both clients, installed to `~/.claude/commands/antz.md` and `~/.config/opencode/commands/antz.md` via the same `install_file`/marker/backup mechanism as agent files. The mechanism differs per client: on Claude Code the command body runs in the main session (which already has the `Agent` tool) and explicitly delegates the request to the `antz-orchestrator` subagent; on OpenCode the command's `agent: antz-orchestrator` frontmatter (with no `subtask`) switches the session to that `mode: primary` agent natively instead of spawning it as a nested subagent.

## Versioning
- `VERSION` (semver) and `CHANGELOG.md` (Keep a Changelog format) track changes to `agents/prompts/`, `agents/meta/`, and `install.sh`. Any commit that changes any of those three must bump `VERSION` and add a matching `CHANGELOG.md` entry in the same commit, regardless of what else that commit contains (a commit touching `agents/` and/or `install.sh` together with docs or tests is still a bump commit). The patch/minor/major gradation is one scale for `agents/` and `install.sh` changes alike: patch for non-behavioral wording tweaks, including `install.sh` comment/string-only tweaks and internal refactors with no change to rendered output or reported behavior; minor for behavior changes, to the roles or to `install.sh`'s install mechanics and rendered commands/agents (rendered bodies, flags, install paths, detection logic, the `--check` report); major for breaking changes to the workflow contract or the rendered command contract (directory layout, access model, the `antz:generated` marker format, the access-to-frontmatter mapping, install locations, etc). A commit touching several tracked paths grades by its most severe component. Changes to docs (`AGENTS.md`, `CLAUDE.md`, `docs/`, `spdd/`) and to `tests/` don't require a bump. Why `install.sh` is tracked: it renders the installed agent and command files directly and embeds the source `VERSION` in each installed file's `antz:generated` marker comment, so an unbumped `install.sh`-only change leaves installed copies silently stale — `./install.sh --check`'s version comparison reports no drift, and the documented bump rule is the only defense against that.
- `install.sh` embeds the source `VERSION` in each installed file's marker comment. Every run compares that to the installed copy's embedded version and, if newer, prints the intervening `CHANGELOG.md` entries before overwriting. `./install.sh --check` only prints that report — no files are written.
- Every `VERSION` bump gets a matching git tag (`vX.Y.Z`) created locally against the commit that makes the bump, in the same change — tags aren't pushed automatically, only on explicit request.
